# 설명 방법

**목적**: 독자 조절을 반복 가능한 판단으로 바꾸되, 친근함보다 사실 충실도를 우선한다.

## 1. 독자 모델 만들기

간접 단서보다 직접 근거를 먼저 사용한다.

| 신호 | 강한 근거 | 과도하게 쓰면 안 되는 약한 근거 |
|---|---|---|
| 지식 | "Python은 알아요", 명시한 수업 수준, 이전 질문 | 나이 또는 직함만으로 한 추정 |
| 목표 | "결정해야 해요", "디버깅을 도와줘", "가르쳐줘" | 맥락 없는 일반적인 "설명해줘" |
| 맥락 | 제공된 코드, 장애, 회의, 수업, 제품 결정 | 지어낸 취미나 가정 내 역할 |
| 제약 | 분량, 전문용어 금지, 필수 용어, 언어 | 추정한 집중 시간이나 지능 |

빠진 정보가 예시만 바꾼다면 중립적인 예시를 골라 계속한다. 빠진 목표나 사전 지식 때문에 설명 자체가 크게 달라질 때만 질문 하나를 한다.

## 2. 인과의 뼈대 보존하기

단순화하기 전에 다음을 식별한다.

1. 설명 대상.
2. 대상이 하는 일 또는 해결하는 문제.
3. 관련 행위자나 부품.
4. 원인과 결과의 순서.
5. 결과나 영향.
6. 빠뜨리면 단순화된 문장이 거짓이 되는 주의점.

용어만 보고 초안을 쓰지 않는다. 작동 원리를 이해하지 못했다면 조사하거나 불확실성을 밝힌다.

## 3. 깊이 고르기

| 독자 목표 | 기본 깊이 | 포함 내용 |
|---|---|---|
| 빠른 방향 파악 | 요지 | 정의 + 중요한 이유 |
| 처음 배우기 | 기초 | 요지 + 구체적 모델 + 작동 원리 + 예시 하나 |
| 의사결정 지원 | 결정 | 결과 + 선택지 + 트레이드오프 + 불확실성 |
| 디버깅 | 진단 | 증상 + 원인 사슬 + 수정 + 검증 |
| 학습/교육 | 학습 | 층위별 작동 원리 + 예시 + 선택적 되말하기 |
| 전문가의 인접 분야 학습 | 비교 | 아는 개념 + 차이 + 경계 사례 + 트레이드오프 |

"쉽게"는 인지 부담을 조절하는 말이지 정확도를 낮추는 말이 아니다. "자세히"는 깊이를 조절하는 말이지 문장을 복잡하게 쓰라는 뜻이 아니다.

## 4. 용어를 잘 쓰기

- 독자가 다시 만나게 될 핵심 용어는 유지한다.
- 처음 나올 때 쉬운 말로 정의한다: **용어 — 실무적 의미**.
- 한 개념에는 한 이름을 일관되게 쓰고, 문체 변화를 위해 동의어를 돌려 쓰지 않는다.
- 사용자가 이미 익숙함을 보이지 않았다면 약어는 한 번 풀어 쓴다.
- 추상 명사 묶음보다 동사와 구체적인 행위자를 선호한다.
- 긴 인과 사슬은 문장 조각이 아니라 순서 있는 단계로 나눈다.

## 5. 비유를 발판으로 쓰기

비유는 선택 사항이다. 설명 비용을 줄일 때만 하나를 쓴다.

### 비유 게이트

1. **친숙성**: 고정관념이 아니라 명시된 맥락에서 친숙할 가능성이 높은가?
2. **대응**: 중요한 각 요소를 실제 작동 원리의 요소에 대응할 수 있는가?
3. **예측**: 비유가 다음에 일어날 일을 예측하는 데 도움이 되는가?
4. **한계**: 중요한 불일치를 짧게 밝힐 수 있는가?

하나라도 아니면 구체적인 실행 예시나 도식형 순서를 대신 쓴다.

좋은 형태:

> 식당 대기줄을 떠올려 보세요. 요청은 처리되기 전에 차례를 기다립니다. 대응은 여기까지입니다. 소프트웨어 큐는 설계에 따라 항목을 복사하거나 재시도하거나 여러 개를 동시에 처리할 수 있습니다.

비유 하나만으로 사실 주장을 떠맡기지 않는다. 실제 작동 원리를 바로 앞이나 뒤에서 이름 붙인다.

## 6. 흔한 자료 유형 설명하기

### 코드

1. 주변 시스템에서 코드가 맡는 목적을 말한다.
2. 입력, 출력, 상태 변화를 이름 붙인다.
3. 실행 순서대로 제어 또는 데이터 흐름을 추적한다.
4. 그 흐름에 중요한 문법만 설명한다.
5. 관련된 부작용, 실패 경로, 트레이드오프를 밝힌다.

### 오류

1. 눈에 보이는 증상을 쉬운 말로 옮긴다.
2. 근거가 뒷받침하는 근본 원인을 찾는다.
3. 원인이 증상으로 이어지는 과정을 연결한다.
4. 요청받았거나 유용하면 가장 작은 수정안을 준다.
5. 검증 또는 재발 방지 단계 하나를 준다.

맥락을 확인하지 않고 오류 문구 자체를 근본 원인으로 취급하지 않는다.

### 비즈니스 또는 관리자 대상

영향과 결정부터 말한다. 위험, 비용, 순서, 트레이드오프를 이해하는 데 필요한 만큼만 기술 작동 원리를 포함한다. 코드 서식을 기계적으로 금지하지 말고, 결정에 도움이 되지 않을 때 뺀다.

기본값은 튜토리얼이 아니라 결정 브리프다. 권고 하나, 이를 뒷받침하는 트레이드오프 최대 세 개, 다음 결정 또는 측정 하나로 구성한다. 요청이 있을 때만 선택적인 작동 원리 세부사항을 브리프 뒤에 둔다. 같은 권고를 요약, 체크리스트, 결론으로 반복하지 않는다.

### 아동과 초보자

짧고 구체적인 문장으로 한 번에 한 생각만 전달한다. 다시 만나게 될 개념의 실제 이름은 유지한다. 아기 말투, 과장된 흥분, 사탕·장난감·게임·만화 같은 관심사를 추정하지 않는다.

### 인접 분야를 배우는 전문가

독자가 익숙하다고 밝힌 개념에서 시작한다. 차이, 불변 조건, 실패 방식, 트레이드오프를 강조한다. 이미 이해를 보인 기초를 다시 가르치지 않는다.

### 안전 중요 주제

의료, 법률, 금융, 보안, 운영 위험 주제에서는 다음을 지킨다.

- 불확실성, 조건, 예외를 유지한다.
- 일반 교육과 개인 맞춤 판단을 구분한다.
- 쉬운 정의 옆에 실제 용어를 유지한다.
- 단순화된 모델이 멈추는 지점을 밝힌다.
- 일반 정보를 확신에 찬 개인 권고로 바꾸지 않는다.

## 7. 이해 확인은 선택적으로 추가하기

사용자가 학습, 공부, 준비, 이해 확인을 요청했을 때만 부담 없는 질문을 최대 하나 쓴다.

되말하기를 선호한다.

> 자신의 말로, 무엇 때문에 재시도가 발생하는지 설명해 보세요.

상식 퀴즈, 갑작스러운 시험, "이해되셨나요?"는 피한다. 일회성 방향 파악, 결정 브리프, 답만 요청한 경우에는 확인 질문이 필요 없다.

## 8. 압축 순서

설명이 너무 길면 다음 순서로 제거한다.

1. 반복 요약.
2. 두 번째 비유나 예시.
3. 장식적인 도입과 전환 문장.
4. 선택적인 역사와 잡학.
5. 우선순위가 낮은 구현 세부사항.

인과 연결, 결정에 중요한 트레이드오프, 안전 주의점, 출처 불확실성을 먼저 제거하지 않는다.

## 9. 발송 전 다시 읽기

첫 문단만 읽어도 질문에 답해야 한다. 그다음 "~와 같다", "떠올려 보세요", "생각해 보세요"가 들어간 모든 문장을 읽고, 대응되는 개념과 중요한 불일치가 가까이에 있는지 확인한다. 마지막으로 예시를 빼고 읽어도 실제 작동 원리가 남아 있어야 한다.
